# ADR-0007: Private CA with OpenSSL, one certificate per service

## Status
Accepted

## Context
Task item 5 requires own web certificates for the services, optionally from an
own (self-signed) CA. Services also talk to each other over TLS (GitLab →
OpenProject webhooks, XWiki → OpenProject API, all → LDAPS), so trust must be
established in several client trust stores, not only in browsers.

## Options considered
- **Self-signed certificate per service** — every client must trust four
  certificates individually, again after every renewal.
- **Private root CA** — one trust anchor; renewed service certificates are
  accepted automatically.
- Tooling: `openssl` (every step visible), `mkcert` (hides SAN/extension
  handling), `step-ca` or Caddy `tls internal` (online CA, key on the server).

## Decision
One private root CA created with `openssl` on the workstation; one leaf
certificate per service (`git.lab.test`, `wiki.lab.test`, `pm.lab.test`,
`ldap.lab.test`); certificate verification stays enabled in every client.

## Design details
| Aspect | Choice | Reason |
|---|---|---|
| Hierarchy | root CA only, no intermediate | four services, three days; production practice (offline root + online intermediate) is noted, not needed |
| Key type | ECDSA P-256 for CA and leaves | modern, small, fast; supported by Caddy, Java 17+, Ruby/OpenSSL, all browsers |
| CA validity | 10 years | renewing the CA means touching every trust store |
| Leaf validity | 365 days (below the 397-day browser convention) | enforces a documented renewal runbook |
| Names | one certificate per service, SAN `DNS:<name>`; no wildcard | task says "for the services"; one key per service limits blast radius |
| Extensions | CA: `basicConstraints=CA:TRUE`, `keyUsage=keyCertSign,cRLSign`; leaves: `CA:FALSE`, `keyUsage=digitalSignature`, `extendedKeyUsage=serverAuth`, `subjectAltName` | browsers ignore CN and require SAN; `serverAuth` is mandatory (https://docs.openssl.org/3.0/man5/x509v3_config/) |
| CA key storage | workstation only, AES-encrypted with passphrase; never on the server | the server is the exposed component; losing it loses four revocable leaf certificates, not the CA |
| In git | scripts and the public `ca.crt` only | lets any admin or reviewer import the CA; private keys never in git |

## Trust distribution (who must trust the CA)
| Client | Talks to | Trust store |
|---|---|---|
| Browser on the workstation | all services via Caddy | Fedora: `/etc/pki/ca-trust/source/anchors/` + `update-ca-trust`; Flatpak browsers do not see it → import in browser settings |
| GitLab | OpenProject (webhooks), lldap (LDAPS) | `/etc/gitlab/trusted-certs/`, symlinked into the embedded OpenSSL store on `gitlab-ctl reconfigure` (https://docs.gitlab.com/omnibus/settings/ssl/) |
| XWiki (Java) | OpenProject API, lldap | JVM trust store (`keytool -importcert` into `cacerts` or a dedicated trust store) |
| OpenProject | lldap, outbound webhooks | mount the CA and set `SSL_CERT_FILE` (OpenProject Docker docs); webhooks reportedly need this explicitly |

Internal name resolution: Caddy carries network aliases for all four hostnames
on the shared Docker network, so containers call the same names as browsers
and the SANs match in both directions.

## Consequences
- Disabling verification (`verify_certificates: false` or similar) is the
  common quick fix for "unable to get local issuer certificate" errors; it is
  explicitly not used, because it makes TLS between services worthless.
- Three different trust-store mechanisms (Ruby, Java, Debian) are expected
  stumbling blocks and are documented in `docs/problems.md`.
- Issuing a certificate is a manual step on the workstation; renewal is a
  runbook entry (issue → copy → reload Caddy → update trust stores).
